# 云端：JupyterHub 上每用户一个 Studio 的本机回环验证

2026-10-29，分支 `cloud-hub`。部署为 `deploy/cloud/compose.yaml` 加 `compose.loopback.yaml`，Compose 项目 `presmium-cloud-trial`，入口 `127.0.0.1:18787`。组件：JupyterHub 5.5.4、oauthenticator 17.4.0、dockerspawner 14.0.0、jupyterhub-idle-culler 2.0.0、jupyter-server-proxy 4.6.0、Keycloak 26.8.1。浏览器为 Playwright 的 Chromium（`playwright-chromium` 1.64.1），由脚本驱动；未使用测试套件。

## 实际运行的路径

| 路径 | 结果 |
| --- | --- |
| 注册与登录 Studio | 在控制台经 Keycloak 注册；点“打开 Studio”后 JupyterHub 经同一 realm 登录，不再输入密码，6 秒后进入 `/user/<sub>/studio/` |
| 文稿与预览 | 打开文稿，预览在 `/user/<sub>/preview/` 下加载，动画可交互；没有失败的请求 |
| 共享 | 控制台“共享”，快照在 10 秒后可以访问；控制台从 Hub API 显示 Studio 状态与文稿 |
| 匿名阅读 | 未登录的浏览器打开 `/s/<链接>`，看到内容来源上的网站 |
| 创建副本 | 新账号（此前从未打开 Studio）点“创建副本”：控制台经 Hub API 创建用户并启动其 Studio，副本提交到该用户工作区（`Fork: 冒泡排序`），浏览器直接打开这份文稿；原作者的工作区没有变化 |
| MCP | 访问令牌经控制台 `/mcp` → Hub → 控制服务 → 工作区服务，MCP 客户端列出 80 个工具并调用 `list_documents`；无效令牌 401 |
| 停止与重新打开 | Studio 停止后再打开，15 秒进入，工作区不变；每个用户一个独立卷 |
| 隔离 | 另一个用户访问他人的 `/user/<sub>/studio/`、`preview/`、`cloud/documents` 均为 403 |
| 界面 | 控制台在亮色与暗色、1400 与 390 宽度四种组合下检查 |

## 运行中发现并已修正

- 控制台为从未登录过 Hub 的用户启动服务器时，Hub 因没有登录状态拒绝（403）：关闭 `refresh_pre_spawn` 与 `auth_refresh_age`，由控制台负责认证。
- 重启 JupyterHub 会停止全部 Studio：设置 `cleanup_servers = False`。
- 从控制台开始的跳转链末端换取 DeepSeek Harness 的 `SameSite=Strict` cookie 失败：扩展的入口改为返回一个由本来源发起跳转的页面。
