# 正文撤消与原生批注标记（2026-10-27）

解决或重新打开批注后，正文撤消直接作用于最近的正文输入。
纯批注标记事务不再占用正文历史，批注实体状态继续由原生批注操作修改。

## 复现与原因

既有隔离 Studio 的私有副本实际完成了“输入 A、创建批注、输入 B、解决批注、撤消、恢复”。
修复前，撤消只把正文批注标记的 `data-orphan` 从 `true` 改为无值；正文 A+B、已解决状态和整个批注实体都不变。
恢复只把 `data-orphan` 改回 `true`，文稿内容依然不变。

BlockNote 0.56.0 的批注扩展用文字标记保存锚点，用 `ThreadStore` 保存批注实体。
`updateMarksFromThreads` 通过原生事务删除、添加标记以同步 `orphan`，默认创建批注也会添加标记；这些事务没有设置 `addToHistory: false`。
ProseMirror 因而将它们记录到正文历史，正文撤消先遇到不修改文稿内容的标记事务。
实际标记变化发生在正文编辑器内，不是撤消指向评论输入框；修复后的编辑器节点探针也确认保存与撤消没有替换正文编辑器。

## 公开事务边界

`comments.ts` 的 `excludeCommentMarkHistory` 使用公开 `BlockNoteEditor.onBeforeChange` 回调，在事务应用前读取 `tr.steps`。
仅当非空步骤全部属于 `AddMarkStep` 或 `RemoveMarkStep`，且标记名称等于当前 `CommentsExtension` 的公开标记名称时，设置 `addToHistory: false`。
没有调用 `getChanges()`、依赖内部路径或修改依赖源码。

`BlockNoteSurface.tsx` 在 `onReady` 前安装回调，在编辑器卸载时取消订阅。
其他文字、格式、结构及混合事务沿用原生历史，不增加跨实体撤消栈。

## 实际结果

原始动作代码、源码前后状态、标记属性及浏览器结果保存在 `.presmium/ui-evidence/document-comment-history-audit.json`。
所有文稿均由真实文稿接口复制到隔离工作区，保存经过实际服务与 `lecture.json`；未改写原 `4320` 用户文稿。
本轮只重建一次隔离客户端，没有重启共享服务。

| 实际动作 | 观察结果 |
|---|---|
| A、批注、B、解决、撤消 | 第一次撤消删除 B，保留 A，已解决状态与锚点不变，标记仍为 `orphan: true` |
| 随后恢复 | 正文精确回到 A+B，整个批注实体不变 |
| A、创建批注、撤消 | 第一次撤消删除 A，批注实体保留，锚点随文字消失 |
| 随后恢复 | 正文、批注及锚点精确恢复 |
| 撤消 B、重新打开批注、恢复 | 正文恢复仍可用，恢复 B 后保持重新打开的状态 |
| 选中 B、原生加粗、撤消、恢复 | DOM 与源码中的加粗一同移除和恢复，批注及段落 ID 不变 |
| 在批注选区内插入“插”、撤消、恢复 | 真实标记文字变为“甲先插说明”，锚点终点从 22 移到 23；撤消精确还原正文和锚点，恢复精确还原整个文稿 |

创建批注后的正文撤消检查首次使用了要求 A 仍存在的定位器；A 已被成功撤消后，定位器超时。
原始错误保留，随后用实际源码和保留的段落前缀确认了撤消与恢复。
一次加粗快捷键探针收尾时焦点在评论输入器，正文没有加粗；随后明确核对原生选区等于 B，再用原生加粗按钮完成了格式检查。
未将这些观察脚本的失败算作产品行为通过。

隔离客户端重建后的首次重载捕获一次宿主 `renderSlot('root') before any 'root' registration (boot order)` 异常，未出现工作区 HTTP 失败。
本轮未调查该宿主启动问题，也未重跑已通过的批注视觉矩阵或其它表格历史。

类型检查通过，覆盖 1156 个文件；分层与差异格式检查通过。
未新增测试，未运行测试套件或全量验证。

## 能力边界

正文撤消不恢复批注的已解决、重新打开、回复或删除状态。
当正文撤消删除了锚点所在文字时，批注实体仍保留；这与纯标记事务不进入正文历史是两件事。
本轮不提供跨批注实体的统一撤消能力。
