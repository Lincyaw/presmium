# 工作台打开与切换讲义：2026-10-21

本文记录按媒介按需启动的第一轮调查，后续有生命周期的 iframe 复用见 [讲义预览缓存记录](preview-cache-2026-10-21.md)。

工作台打开讲义的等待包含三部分：请求预览地址、启动当前文稿的开发服务器、iframe 加载模块并初始化。之前的增量编译数据只覆盖编译，不能代表这条完整链路。本次去掉了网页请求等待 Slidev 的开销；页面整体仍未达到 100 ms。

## 保留的修改

工作台请求 `preview?document=…&view=web`，返回网页地址与配置中可用的幻灯片入口，切到幻灯片才等待 Slidev。显式请求幻灯片时保留真实启动错误，等待或失败时仍可返回网页；未传 `view` 的调用保持旧版启动行为。客户端按文稿、媒介、请求序号接受答复，避免快速切换后被旧请求覆盖。

同一个隔离服务、一份很小的 web + slides 文稿，按以下顺序测量：

| 请求 | 实际等待 |
|---|---:|
| 首次 `view=web`，含文稿就绪 | 74.85 ms |
| 未传 `view` 的旧调用，文稿此时已编译，仍需启动 Slidev | 3536.10 ms |
| 再次 `view=web` | 2.52 ms |
| Slidev 就绪后 `view=slides` | 2.23 ms |

这组数据证明移除了额外等待，**不是整页从 3.54 秒降到 75 ms**。只配置网页的讲义原本就不启动 Slidev，因此这处修复不消除它们的模块加载成本。

## 完整页面的观察

使用真正的 Studio、工作区服务和 Chromium，先打开两份工作台 fixture 讲义，再交替返回三次。计时从点击开始，直到预览协议 ready 且 iframe 首章节可见；首页、服务启动另计。默认原生线程预算为 1、libuv 为 2，没有提高并发。

最初探测中，两份讲义首次打开分别为 5935 / 5333 ms，三次返回为 324 / 338 / 330 ms。每次页面加载约 340 个模块及其他请求。切回讲义会重新创建 iframe，模块请求与运行时初始化随之重做；开发依赖首次优化也会阻塞页面的关键模块。

最终代码的独立探测中，两次首次打开为 18709 / 19465 ms，三次返回为 841 / 878 / 836 ms，没有浏览器页面错误。最初与最终探测开始时的一分钟系统负载分别为 4.43 / 25.82，本机为 10 个逻辑处理器；测试期间仓库还有并行源码修改，不能据此计算整页优化的前后比例。这些数据用于记录可重现的链路与剩余成本，而非宣称整页提速。

试过的配置包括：提前发布依赖优化结果、指定扫描入口、将源码链接纳入依赖分析、预打包安全的 JS 依赖、预热主题入口，以及关闭自动依赖发现的组合。没有测出稳定的整页收益；其中仅扩大源码依赖分析还将请求数增至约 3130。**这些实验代码均已撤回**，未保留额外的扫描、缓存或预热负担。

剩余工作是减少工作台预览反复加载开发模块的成本。若要复用 iframe，先需要明确暂停与恢复执行器、媒体、插件和订阅的生命周期；简单隐藏旧 iframe 会留下后台工作。此轮未采用这种做法，也未取消资源预算；后续实现和测量见上方缓存记录。

## 复现与验证范围

在已安装依赖与 Chromium 的源码检出中运行：

```sh
GOMAXPROCS=1 RAYON_NUM_THREADS=1 UV_THREADPOOL_SIZE=2 \
  node scripts/bench-workbench-preview.mjs /private/tmp/preview.json --rounds 3
```

脚本只启动一套隔离服务与 Chromium，结束时关闭并清理；记录首开、返回、请求计数、页面错误、启动时间和系统负载，不输出服务令牌。它不构建完整示例，不启动模型，也不运行测试套件。它记录时间，不用固定延迟阈值作功能断言。

验证通过：`packages/workspace/test/preview-forms.test.ts` 的一个真实服务用例（约 5.3 秒）；`e2e/preview-loading.spec.ts` 的一个 Chromium 用例（约 25.9 秒），覆盖网页首开、幻灯片启动中返回网页、晚到答复之后仍停留在网页；分层、技能与改动空白检查。浏览器回归首轮因选择器使用了错误的可访问性角色而失败，修正后通过。另运行了上述工作台探测。没有运行全量测试或完整 demo 构建。原始数据见 [JSON](workbench-preview-2026-10-21.json)。
