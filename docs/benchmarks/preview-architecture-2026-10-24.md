# 预览性能与编译式架构评估（2026-10-24）

> 历史基线：本文基于 `3544a7d5` 及当时的本地改动。远程更新至 `7231a7ee` 后，Slidev 与 VitePress 已移除，网页和幻灯片均采用自有预编译查看器；下文的 Slidev 故障、测试路径与架构建议不代表当前实现。保留此记录用于比较，当前调试方法见 [调试预览加载与卡顿](../debugging.md)。

保留编译器、IR 和固定查看器，优先消除交互路径中的重复启动。当前证据不支持为了性能把 React、Vue、编辑、插件和编译器全部推倒重写。高保真的 Slidev 首次预览仍有明显成本，不能用网页和视频的热切换改善来宣称它已经解决。

## 观察与根因

原现场在文档、幻灯片和视频之间切换时会长时间等待。一次隔离观测中，幻灯片约 24 秒才握手、40 秒才出现内容；这两件事都晚于后端准备好地址。当前问题属于加载与生命周期的性能问题，同时包含启动时序错误。

排查了三种解释：

| 假设 | 证据与判断 |
|---|---|
| 语音引擎报错拖慢所有视图 | 文稿有 16 句改写后的讲解不在旧缓存中，未配置 edge 引擎，视频导出因此失败。但预览仍能返回带字幕的静音讲授；这不能解释 Slidev 模块的长时间加载 |
| React／Vue 本身使切换很慢 | 文档、放映共用页面时已经很快。视频先前用了单独 iframe；两个缓存位置要容纳文档、视频与 Slidev 三种页面，部分往返会淘汰页面。消除这项重载后，视频切换不再需要重新执行整套模块，因此不必先换框架 |
| 开发服务器、资源压力和初始化时序共同放大等待 | Slidev 启动后仍要转换和加载开发模块；机器负载一度超过 30，交互档按现有预算取到单线程。低负载复测时也仍有冷加载成本。另发现 ready 早于异步视图注册，第一次进入视频的命令可能被忽略，表现为无限等待 |

FloatingVue 的异常是已知的上游问题，见 `architecture.md` 9.3 节；页面仍能显示，不能仅凭这条日志把它认作整个等待的根因。Wake Lock 拒绝来自嵌入页尝试请求屏幕常亮，已在嵌入预览中关闭。Slidev 开发态仍有 `POST /@server-reactive/nav` 的 404，这是根路径同步接口与带路径前缀的预览之间的兼容问题，尚未修复；不通过改写第三方源码或放宽请求检查来掩盖它。

## 本轮保留的改动

- 同一文稿的文档、放映、视频共用一个预编译查看器和 iframe，经 `go.view` 切换；缓存按文稿与渲染端划分，视频不再占用第三种页面的位置。
- 离开视频时释放播放器、媒体与讲授选择。保存后仍读取最新编译结果，再次进入视频时读取当前讲授轨。
- 网页预览保留最新导航请求，等待异步视图注册且可用后再执行；覆盖冷启动时第一次直接进入视频的情况。
- 嵌入式 Slidev 预览不启动内置录制、演讲者模式或屏幕常亮。独立放映与正式产物沿用原配置。
- Slidev 子进程打印就绪地址之后仍持续转发输出，启动后的 Vite 和浏览器转发错误不再丢失。

扩大 ESM 预打包的实验没有保留：将所有第三方 ESM 一并打包会让一个优化分块从生成项目根目录导入 `@vueuse/shared`，该位置无法解析它，导致 500。选择性调整也没有获得足以独立归因的冷启动收益，最终恢复原有依赖处理。Vite 官方说明了[依赖预打包、链接依赖与重新发现依赖后的重载](https://vite.dev/guide/dep-pre-bundling.html)；不能在不了解框架排除项的情况下把所有依赖强行合并。

## 实测与边界

文稿为当前 `.presmium/example-workspace` 的 `libraries`，包含五种动画库和已改写的讲解。每轮均为独立服务状态与 Chromium；按真实界面点击，等待握手及实际章节、幻灯片版式或讲授播放器出现。耗时包含浏览器自动化的点击与观察开销，不是纯 CPU 时间。

最终版本单独运行（本轮没有并行运行测试）：

| 操作 | 本轮耗时 |
|---|---:|
| 第一次打开文稿（包括冷编译与查看器准备） | 3.20 秒 |
| 首次进入 Slidev 幻灯片 | 6.16 秒 |
| 从幻灯片返回文档 | 0.51 秒 |
| 再次进入 Slidev 幻灯片 | 0.39 秒 |
| 从幻灯片进入视频 | 0.41 秒 |
| 视频返回文档 | 0.04 秒 |
| 同一页面再进入视频 | 0.13 秒 |

另一次只切换文档与视频的验证中，进入视频为 112～115 毫秒，返回文档为 30～31 毫秒。浏览器集成用例额外验证了 iframe 身份不变、没有新的查看器页面请求、播放器退出和保存后更新。

早期基线首次进入幻灯片为 20.08 秒、视频为 0.93～1.10 秒。**这不能作为严格的百分比提升**：期间整机负载与空闲内存变化很大，较晚采样为 10 个逻辑处理器、负载约 5.8、空闲内存约 0.85 GiB；已有后台进程未被测试停止。可靠结论是页面重载被消除、热切换明显缩短、视频启动指令不再丢失；Slidev 冷加载依然是独立瓶颈。

本机原始记录：`.presmium/debug/perf-before/`、`perf-shared-view/`、`perf-final-idle/`。这些目录被 git 忽略。复现最终顺序：

```sh
pnpm debug:studio .presmium/example-workspace --document libraries --views document,slides,document,slides,video,document,video --timeout 30000
```

调试命令即使完成所有切换，捕获到上述上游错误或 404 时仍以非零状态退出，不能把它当作“没有前端报错”。

定向验证通过：`e2e/export.spec.ts` 的共享查看器与修改更新用例；`e2e/preview-protocol.spec.ts` 的网页命令、选区、IR 更新与错误上报用例；`packages/workspace/test/preview-forms.test.ts` 的按需预览与嵌入配置用例；`packages/render-slides/test/plugins.test.ts` 的已安装 Vue 源码依赖、保存更新与移除 Vite 插件用例。类型、分层与技能检查通过。没有运行全量测试、全部示例构建、消费者打包安装或视频编码导出。

## 如何借鉴 Overleaf

[Overleaf 的编译流程](https://docs.overleaf.com/getting-started/recompiling-your-project)将源码编辑与 PDF 产物分开，支持手动编译、每隔数秒自动编译，并在可能时保留编译辅助文件。这适合借鉴的是生命周期：编辑器常驻、编译有状态、预览消费产物、错误有位置。

Presmium 的 MyST → IR 本来就是编译管线；网页固定查看器也已经把共享运行时和文稿代码分开构建。下一步应沿着这个边界收敛：

1. **常驻编辑器与查看器。** 文档、演示、讲授是同一查看器的视图。普通文字修改只编译受影响内容并发布新 IR，不重建运行时、依赖或整个网站。
2. **独立的文稿代码构建。** 组件或场景代码变化才重建对应代码包；按依赖指纹复用，旧任务完成不能覆盖较新的修订。
3. **Slidev 作为精确预览与发布任务。** 平时编辑使用固定查看器；需要核对 Slidev 的版式时才准备它。若进一步改为后台生成精确预览，应在生成期间保留上一份成功产物，并明确标出它对应的修订，不能把旧画面冒充最新结果。
4. **文本编辑作为可选交互模式。** 可以提供类似 Overleaf 的源码与预览分栏，复用现有源码读写、审阅、撤消和编译接口。IR 已有源码位置，可用于编辑器与预览的双向定位。编辑器按需加载，不能再给预览绑进一整套开发服务器。是否以源码为默认界面是面向用户的产品选择，不是性能修复的前提。

“每次修改完整构建一次 VitePress／Slidev 站点”会把浏览器等待换成整站构建等待，不是这里推荐的编译式预览。完全生成 PDF 或图片也会失去现场运行、动画时间轴和课堂互动。更合适的产物是**预编译共享运行时 + 增量文稿数据 + 按需代码包**，精确版式和视频文件异步生成。

若固定运行时下的纯文字保存到画面更新仍持续超过 300 毫秒，先测编译与 IR 发布；若无重载时仅 DOM 更新仍阻塞，再优化渲染粒度。只有确认这些边界仍然无法满足目标，且真实瓶颈落在框架调度或布局本身，才有充分理由替换渲染技术。当前证据尚未达到需要从头重写的程度。
