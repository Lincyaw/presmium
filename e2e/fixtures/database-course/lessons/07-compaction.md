# 单元 7：过滤、归并与空间回收

(bloom-filter)=
## Bloom filter 只回答“肯定没有”或“可能有”

点查一个不存在的键时，多张有重叠键范围的 SSTable 都可能成为候选。每张表保存一个 Bloom filter，若过滤器判不存在，可直接跳过读取；判可能存在仍需读盘确认。所有已插入键都必须通过过滤器，否则会把真实数据隐藏。

:::{slide}
| 过滤结果 | 下一步 |
|---|---|
| 肯定不存在 | 跳过这张表 |
| 可能存在 | 继续稀疏索引与文件查询 |
:::

本课使用确定性哈希构造过滤器，不用带进程随机化的 Python `hash()` 写持久文件。约 $m$ 个 bit、$n$ 个键、$k$ 次哈希的理想误判率为 $(1-e^{-kn/m})^k$；这是模型估计，实测还受键分布、哈希与取整影响。benchmark 使用位于各表键范围内的缺失键，避免把 min/max 范围过滤的收益误算给 Bloom。

(range-merge)=
## 范围扫描：多个有序来源，取每个键的最新版本

:::{hints}
slides: { zoom: 0.76 }
:::

一次范围读取可能遇到 memtable、多个 SSTable 中的重复键。按键做多路归并，相同键按序号选择最新版本；最新版本若是墓碑，就不输出。扫描按 `[start,end)` 返回有序键值。

:::{slide}
```text
run A: Ada=10, Lin=7
run B: Ada=12, Lin=DELETE
merge: Ada=12
```
:::

不能把每张表全部读入一个字典再排序，随后声称这是流式 LSM 范围扫描。课程实现的归并迭代器只保留各输入当前位置及堆中的候选；memtable 自身排序仍受其上限约束。范围扫描不从 Bloom 获益，过滤器对整段区间通常不能做逐键排除。

(compaction-safety)=
## 压缩先写新文件，成功发布以后再删旧文件

追加日志通过重写存活键回收旧版本；LSM 通过多路归并把多个 run 合成新表。两者都必须保证发布前后总有一套完整可恢复的数据。临时文件与目标处于同一文件系统，提交使用替换并按要求同步文件与目录。

:::{slide}
:reveal: items
- 新文件构建失败：旧集合仍可用
- 发布成功：重启只读取新集合
- 旧文件删除失败：留下垃圾，不能丢有效数据
- 全部旧版本被覆盖，才可安全丢弃墓碑
:::

本课全量压缩覆盖所有 run，所以能回收已无更老版本的墓碑。若只压缩部分层，就不能照搬这个规则。压缩同时消耗 CPU、读写带宽和临时空间；即便文件变小，也可能使前台延迟变差。

(compaction-lab)=
## 实验：空间收益和恢复收益分别是多少？

固定存活键数，连续覆盖若干轮并删除一部分键。测压缩前后的文件总字节、压缩本身耗时、重开耗时和查询结果，最后再次重开确认被删的键没有复活。

```bash
python3 code/demos.py compact --data lab-data/compaction
```

该命令输出单次课堂观测的 `compact_ms`、压缩前后 `reopen_*_ms`、恢复解码记录数和文件字节。它帮助解释工作量变化；正式性能结论仍使用第 8 单元的预热与重复采样，不能把一次运行的耗时比当成稳定加速比。

:::{slide}
| 指标 | 必须同时回答的问题 |
|---|---|
| 文件缩小多少 | 哪些旧版本与墓碑被回收？ |
| 恢复快多少 | 是否真的少扫描了记录？ |
| 压缩花多久 | 期间需要多少临时空间？ |
| 正确性 | 最新值与删除是否保持？ |
:::

作业：改变更新轮数，再测一组。若历史很少，压缩可能几乎没有空间收益；如果把这组负结果删掉，课程就无法说明什么时候值得压缩。

(lsm-compact-implementation)=
## 实现：覆盖所有 run 后才回收墓碑

:::{hints}
slides: { zoom: 0.6 }
:::

逐行对应“先 flush → 流式归并全部 run → 生成新表 → 发布 manifest → 删除旧文件”。无论日常写入策略如何，回收旧文件的压缩都会采用同步发布协议。

如果新表写入或 manifest 替换失败，旧集合仍保留；替换成功后，旧文件才变成可回收垃圾。全量压缩的墓碑规则不能直接移植到只选择部分 run 或部分层的算法。
