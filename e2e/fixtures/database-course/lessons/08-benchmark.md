# 单元 8：用证据解释优化

(benchmark-method)=
## 公平对照先于“快了多少倍”

benchmark 先生成固定种子的键、值和操作轨迹，再交替或随机排列被测实现。每轮使用独立文件目录，先核对结果，预热后再计时。正式结果保留至少五轮的原始样本；计时用单调高精度时钟。

:::{slide}
:reveal: items
- 相同数据、相同命中率、相同操作与提交粒度
- `none` 与 `fsync` 分开，不用较弱语义冒充优化
- 中位吞吐、操作延迟、空间、恢复与逻辑读写一起看
- 保留 raw JSON/CSV、环境信息、种子和源码摘要
:::

原始数据区分每个操作的延迟与每轮耗时。五轮中位数能降低偶发扰动，不能用五个总耗时计算一个“每请求 p95”冒充尾延迟。`ops/s` 的分母只含该项测量的工作；建库、flush 和打开是否计入，要在表中明确。

本机测量使用真实文件，但没有驱逐操作系统页缓存，因此是页缓存可能命中的工作负载，不称为冷盘或裸 SSD 带宽。小规模 Python 结果可以验证机制与成本趋势，不能外推为生产数据库排名。

(benchmark-interpretation)=
## 倍数必须能解释，也必须允许没有提升

对同一项任务，延迟加速比是 $T_{baseline}/T_{candidate}$；吞吐提升比是 $Q_{candidate}/Q_{baseline}$。小于 1 就是该项变慢。数据量、值大小、提交策略或命中率不同的两行，不能用这两个公式包装成公平对照。

:::{slide}
| 观察 | 应该追问 |
|---|---|
| 索引点查大幅加速 | 内存与启动成本增加多少？ |
| 批量同步吞吐提高 | 批次等待与确认语义如何变化？ |
| Bloom 少读很多表 | 哈希 CPU 成本是否抵消收益？ |
| 压缩后恢复更快 | 压缩耗时与临时空间是多少？ |
:::

SQLite 对照帮助判断 Python 固定开销与成熟实现的差距，不说明两种数据库已提供同样的事务、查询优化和并发能力。配置和事务粒度必须在报告中公开；若课程引擎更慢，应直接解释，而不是隐藏对照。

(capstone)=
## 结课实验：提出优化，留下可复现的证据

选择一个瓶颈，提交假设、改动、不变量、故障测试和 benchmark。建议方向包括 SSTable 块大小、Bloom bits/key、flush 阈值、恢复 checkpoint、值分离或分层压缩。一次只改变一个主要变量，先保留原始实现供对照。

:::{slide}
结课提交：源码与文件格式说明、重启/故障验证、原始采样、结果解释，以及一个没有变快的场景。
:::

验收比例建议：正确性与恢复 40%，实验设计与可复现性 30%，机制解释 20%，课堂展示 10%。没有通过恢复测试的吞吐数字不进入“优化完成”的结论。
