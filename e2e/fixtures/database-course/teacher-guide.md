### 怎样从零推进，而不是展示成品

完整实现放在 `code/engine.py` 与 `code/lsm.py` 作为可运行的参考答案。授课时在独立的 `lab-data/student-implementation.py` 中从接口写起，按单元实现，保持参考实现不变；学生可对照相同的操作轨迹定位差异。教师先运行参考版验证环境，再让 agent 或学生分步编辑自己的版本。不要在还未实现恢复语义时直接跑吞吐并宣布成功。

每次课建议这样分配：10–15 分钟提出故障或性能问题，15–25 分钟推演文件状态与读取路径，20–30 分钟编码与运行，15–20 分钟对照验证及讲解。实验尚未完成时延至课后，不能把上述时间看成所有班级都能保证完成的进度。

在 Studio 中把源码与预览并排，点选讲义中的源码片段定位到对应文件。专业编码可使用 VS Code；教师通过 agent 分阶段修改，要求每次先描述维护的不变量、再给实现、最后运行真实验证。代码引用与讲义只展示本步需要的片段，完整错误仍保留在诊断中。

给 agent 的任务卡示例：

> 保持 `put/get/delete/write_batch/scan` 接口，为学生版加入 key→文件偏移索引。不要把值常驻索引。先解释“索引只指向完整、已确认追加的帧”的不变量；实现后用独立进程重开，比较同一文件上的命中与未命中结果及读取帧数。只报告实际运行结果，失败时保留文件和 traceback。

所有 native 命令在包含 `code/` 的课程目录运行。正式 benchmark 启动后不要同时构建讲义或运行其他性能实验，减少资源竞争；记录测量环境，不把它称为独占机器实验。

(lab-files)=
## 实验 1：一份文件怎样成为一个数据库

先让学生只实现磁盘快照，不引入日志。展示空文件、空 JSON 对象、已有数据文件三种启动情形，讨论空文件是否等于合法空库。本实现只把不存在的路径初始化为空对象，格式不合法的已有文件报错，避免“重开自动清空损坏数据”。

编码顺序：定义键与值约束；读取快照；完成单条 `put`；统一为 `write_batch`；加入临时文件替换；最后实现删除与范围扫描。每一步都先写一条能通过进程 B 观察的断言。教师运行 `demos.py write/read` 后打开 `snapshot.json`，让学生把文件里的 UTF-8 字节与返回的 Python 对象对应起来。

输入集合至少包含中文键、`None`、布尔值、嵌套列表、重复更新和删除不存在键。`get("nullable", sentinel)` 应返回 `None`，`get("absent", sentinel)` 应返回 sentinel。为了保持 JSON 语义，不接受 NaN 或把任意 Python 对象直接 pickle；这不是序列化安全课，但边界不能含糊。

检查失败路径：故意把文件改成只有半个 `{`，重开必须报告损坏且保留原字节。故意传入无效批次，文件在调用前后必须完全一致。讨论 `write_batch` 里第二项不合法时，为什么不能已经写入第一项。

交付：实现文件、两个独立进程的输出、数据文件大小、至少四种边界输入的结果。说明自己是否已经实现同步；还没实现时不写“断电安全”。

(lab-log)=
## 实验 2：在十六进制里找到记录边界

先在纸上写出三条操作：`put("a",1)`、`put("a",2)`、`delete("a")`。每批一帧，下一帧的偏移等于当前偏移加 8 字节帧头再加 UTF-8 负载字节数。键换成中文以后，字符串字符数不等于字节数；应以编码后的 bytes 计算长度。

让学生实现 `encode_frame` 与 `read_frame`，不要先写索引。读取器返回有效帧、正常 EOF、不完整末尾、完整损坏四种情况。完整帧只有在长度上限、CRC、JSON 结构与操作约束全部通过后才允许应用。删除必须是一种操作，不能拿正常值 `None` 来偷换。

教师现场把最后一个负载字节翻转，观察 CRC 报错；随后只截短最后一帧，观察恢复器保留已提交前缀。两次实验在数据副本上进行，保留未修改的原件。强调 CRC 检错与物理落盘是不同层次。

未加索引时，点查顺序扫完整日志，保留最新匹配值；删除之后不能返回旧版本。统计同一键被覆盖十次后，文件为何没有变小。让学生估算第十次查询要解析多少帧，再用 `records_read` 对照。

交付：格式说明、逐帧偏移表、正常/截断/校验失败的三份输出，以及删除后重开结果。不要提交一张只显示 Python 字典的截图作为磁盘证据。

(lab-index)=
## 实验 3：索引的加速从哪里来

学生先在重开路径扫描日志建立 keydir。对于批次中同一键出现两次，索引必须指向最后一次操作的序号；对于最新删除，应从存活索引移除。索引发布晚于文件追加与选定的同步边界，写入失败后索引不能指向不存在的位置。

先运行 `python3 code/demos.py index --data lab-data/index`：同一文件、同一键，输出扫描版和索引版的帧数与字节数。命中后仍应出现真实的文件读取；未命中则允许索引直接返回，这项收益不能叫“SSD 随机读取更快”。

再看三种不同成本：点查、范围扫描、启动重建。当前哈希索引的范围扫描先排序所有键，不是有序树；重开也要扫描全部历史。要求学生解释哪个成本由数据量决定、哪个成本由历史版本数决定。将一个键反复更新数千次，可以在存活键数不变时增加恢复成本。

正式测量前预测随 N 的曲线。若扫描记录数随 N 增加而索引命中记录数接近常数，但耗时并不严格线性，列出解码、系统调用与缓存的解释；不能仅凭结果不符合预想就删除样本。

交付：三种 N 的同轨迹结果、内存索引内容示例、重开成本，以及一个索引不解决的问题。完整耗时证据来自正式 `raw.json`，课堂单次观测仅用于调试。

(lab-durability)=
## 实验 4：相同吞吐数字背后可能是不同承诺

先分别运行 `sync=none` 与 `sync=fsync`，观察代码中实际调用位置与 `syncs` 计数。提出一个判断题：写入进程异常退出后数据还在，是否足以证明断电后也在？答案是否定的，因为内核页缓存没有随进程退出而消失。

让学生构造余额转移：Ada 从 100 到 90，Lin 从 100 到 110。两次单条提交之间可以异常退出；合并为一个帧以后，恢复只能应用整批。另测一个非法批次，必须在任何文件变化前拒绝。

把 192 个更新按 batch=1 与 batch=32 提交。前者 192 个提交延迟样本，后者只有 6 个；p95 的单位必须是事务。总操作吞吐可以比较，但不能把 batch 的耗时除以 32 后当成每请求尾延迟，更不能省掉现实服务中组批等待时间。

让学生找出三个持久化层次：日志数据同步、快照替换所需的目录同步、LSM manifest 的发布顺序。文件系统和设备承诺不由 Python 控制；工程报告必须写清使用了什么系统调用和测试了哪类故障。

交付：批次原子性证据、同步次数、两组相同语义的性能比较，以及“本实现不提供隔离”的具体例子。并发客户、锁与后台 group commit 是扩展题，不能通过把函数命名为 transaction 自动获得。

(lab-recovery)=
## 实验 5：恢复器也需要一个失败规范

建立故障表，列出输入文件、恢复结果、是否允许修改文件和期望保留的数据。末尾不完整时只允许截断未提交尾部；完整 CRC 错误、无效操作或中间损坏必须报错且保留现场。尾部长度字段受损可能被误认为半帧，本格式的限制必须在规范里写出来。

阅读 `verify.py` 的独立子进程动作，先确认真实退出码而不是正常 `close`。随后解释四种代表截断位置各覆盖什么：帧头未完成、帧头刚完成、负载一部分、接近完整。完整批次作为对照，证明测试没有把所有新记录都丢弃。

最后读取磁盘原字节摘要，确保损坏报错没有触发自动清空。恢复后再追加一笔并重开，验证截断位置正确；如果仍从错误偏移追加，即使第一次恢复读对，也会污染后续文件。

课堂扩展：为什么“捕获所有异常然后 return None”很危险？它会把权限错误、设备 I/O 错误、校验失败与键不存在混在一起。学生应能让调用者区分损坏和正常未命中。

交付：故障矩阵、子进程退出与重开日志、文件前后摘要、恢复后再写结果。不要把进程退出实验称为真实断电测试。

(lab-lsm)=
## 实验 6：一张表何时正式属于数据库

把 memtable_limit 降到 4、block_records 降到 2。写入 12 个补零字符串键，观察出现多张 `.sst` 与 `.index` 文件。关闭后另开进程查询，证明取值来自被 manifest 引用的磁盘表，不能只观察还在内存中的 memtable。

逐步跟踪序号：当前 manifest 的 flushed_seq=4，WAL 里有第 5、6、7 批。flush 把它们写入新表并发布 flushed_seq=7；如果此刻崩溃而 WAL 还没清，恢复跳过不大于 7 的批次。若在 manifest 发布之前崩溃，旧 manifest 保留，WAL 中 5–7 仍需重放。

沿源码 `write_batch → flush → _write_run → _replace_manifest → truncate` 演示。每个阶段问“现在把进程停掉，重启靠哪份证据”。重点是先后关系，不能用“写完后都 flush 一次”替代协议。

检查目录异常：丢失 manifest、丢失 WAL、缺失已引用表、SSTable 在完整记录边界被截短，都必须明确拒绝，而不是初始化空库或把它当正常 miss。未引用的临时文件可以清理，但必须确认它真的不在有效集合中。

交付：目录布局、稀疏 key-offset 索引示例、两个 manifest 崩溃边界的恢复结果、一次缺文件拒绝。说明 memtable_limit 是触发阈值而非严格内存配额，超大原子批次会带来瞬时内存开销。

(lab-compaction)=
## 实验 7：删除为什么可能复活

先在旧 run 写 `a=1`，新 run 写 `delete a`。如果只压缩新 run 并把墓碑扔掉，旧表仍保留 `a=1`，点查会让它复活。本课只在覆盖全部 run 的合并中回收墓碑，学生必须能够解释这一前提。

范围归并使用一个小例子手算：旧表有 `a=1,c=3`，新表有 `a=2,b=4,c=DELETE`，memtable 有 `b=5`。预期 `[a,b,c)` 是 a=2、b=5。归并先按键排序，相同键选最大序号，再处理墓碑；先过滤旧墓碑再选版本是错误顺序。

Bloom 对照使用表键范围内缺失的键，而非远小于最小键或远大于最大键。先统计表读取次数，再测耗时；如果键范围检查已经排除所有表，就没有测到 Bloom 的收益。对 range on/off 的小差异保持克制，因为 range 路径根本不查 Bloom，噪声不能归因为算法优化。

压缩实验同时记录文件缩减、重开成本、压缩本身耗时和强制同步。单次 `demos.py compact` 便于课堂观察，正式报告使用多轮 benchmark。压缩重写时可能同时保留新旧两份文件，运行需要临时磁盘空间，测量的最终文件大小不是峰值空间。

交付：墓碑复活反例、正确范围结果、Bloom 开关统计、空间与时间报告。若只测热数据命中或几乎没有历史的数据库，可以得到没有改善的结果，这也是有效证据。

(lab-benchmark)=
## 实验 8：写一份可以被复查的性能报告

先运行 correctness gate，再运行一次 smoke 检查矩阵和输出格式，最后使用至少一轮预热与五轮正式样本。保持代码哈希固定，不在测量中途调整实现；若发现正确性问题，停止并修复，重新开始整次采样。

审计一行结果：找到它的 case、N、seed、durability、batch、trace checksum；从 `raw.json` 取全部 latency_ns 重算 nearest-rank p95，再从每轮 logical_operations / elapsed 求吞吐并取中位数。若重算与表格不同，先排查分组和单位。

同 N 的实现共享操作轨迹。写测试预置相同数据后仅测覆盖更新，读测试把建库和打开移到计时外，恢复另立指标。文件字节是目录里数据、索引及打开时 SQLite WAL/SHM 的总和；不同格式有不同语义，不能把它当成应用有效数据字节。

要求每组写三句话：实测比值是多少；逻辑计数能否解释；代价转移到哪里。至少保留一个负收益，例如 Bloom 的哈希开销、LSM 比单表索引更慢，或自制引擎落后 SQLite。没有测 RAM、冷盘、后台压缩尾延迟，就不要给这些方面下结论。

交付：原始 JSON/CSV、环境、源码摘要、命令、结果表、负结果和限制。讨论生产化还缺的 MVCC、锁、层级压缩、备份与校验机制，区分“已经实现”“实验验证”和“下一步计划”。
